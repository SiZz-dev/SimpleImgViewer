# 조직별 원본 누적 용량 제한

## 설치 옵션

~~~yaml
imagegate:
  upload:
    tenant-original-max-bytes: 107374182400 # 조직마다 100 GiB
~~~

기본값은0(비활성), 허용 범위는0~1125899906842624바이트(1 PiB)입니다. config/imagegate.example.yml에서 옵션을 확인하고 저장소 밖의 비밀정보 없이 실제 config/imagegate.yml에 지정한 뒤 재시작합니다. 양수는 모든 조직에 각각 적용되는 공통 한도이며 사용자별/조직별 개별 예외 표는 제공하지 않습니다. 조직은 요청 파라미터가 아니라 기존 신뢰 ViewerPrincipal의 tenantId로 결정합니다. 대소문자가 다른 조직 ID는 기존 저장소와 같이 별개입니다. 인증·CSRF·소유자/파일 권한·설치 형식 정책을 대체하지 않습니다.

## 계수와 예약

기본 LocalMediaStore가 등록한 이미지·영상·음성의 원본 본문 바이트를 조직 내 모든 소유자에 걸쳐 합산합니다. 동일 파일의 중복 등록도 각각 차지합니다. 카탈로그 메타데이터/디렉터리/파일시스템 블록·스탬프·주석·변환 캐시·Servlet 수신 임시 파일·로그는 포함하지 않습니다. 원본 논리 바이트 한도이며 전체 디스크의 물리적 하드 할당량이 아닙니다. min-free-bytes와 각 경로의 OS 볼륨 할당량/모니터링을 계속 사용합니다. 별도 MediaStore 구현은 해당 저장소의 트랜잭션 정책으로 동일 계약을 구현해야 합니다.

해당 조직의 활성 등록이 없을 때 첫 등록은 고정 깊이로 카탈로그·실제 파일 크기를 확인합니다. 이후 동시에 진행하는 등록들은 같은 사용량/예약량을 공유합니다. 신뢰하지 않는 Content-Length나 최대 파일 크기를 선예약하지 않고 실제 읽은 각 버퍼를 디스크에 쓰기 전에 예약합니다. 확정 사용량 + 진행 중 예약량 + 다음 버퍼가 한도를 초과하면 게시하지 않고507 TENANT_STORAGE_QUOTA_EXCEEDED/no-store ProblemDetail로 거절합니다. 원시 경로·조직명·남은 바이트는 응답하지 않습니다. 뷰어는 관리자 문의 안내를 표시하며 자동 재전송하지 않습니다.

정상 등록은 staging 디렉터리의 원자적 게시 직후 예약량을 확정 사용량으로 전환합니다. 실패 시 기존 정리 경로가 미게시 파일을 제거한 다음 예약을 해제합니다. 중복 close는 한 번만 해제합니다. 다른 활성 등록이 있으면 확정 용량과 예약량을 그대로 유지하며 마지막 등록 종료 후 조직 상태를 메모리에서 제거합니다. 유휴 조직 목록/사용자 목록을 무한 캐시하지 않습니다. 정리 자체가 실패하면 용량을 확보했다고 가정하지 않고, 해당 저장소 인스턴스의 후속 등록을503 STORAGE_UNAVAILABLE로 거절합니다. 원인 점검 후 재시작하여 재계수해야 하며 정상 원본 조회는 유지합니다.

용량 조정·손상·한도 초과가 기존 원본 삭제나 권한 회수를 유발하지 않습니다. 예를 들어100 GiB를 저장한 조직의 한도를90 GiB로 낮추면 추가 등록만 거절하고 기존 파일은 기존 권한으로 조회합니다. 실제 원본 삭제/보존 정책이나 용량 관리 HTTP API는 이번 범위에 추가하지 않습니다. 용량 실패가 다른 조직의 정상 등록을 막지는 않으나 저장소 정리 실패로 계수가 불확실해진 경우에는 전체 등록을 보수적으로 중지합니다.

## 재시작과 비정상 종료

영구 누적 카운터 파일을 신뢰하지 않습니다. 재시작 후 첫 등록에서 실제 원본 크기를 다시 확인하므로 이전 실행의 메모리 예약은 재사용하지 않습니다. 알려진 .upload-UUID 잔재의 pending 또는 original.*도 실제 크기로 보수적으로 합산합니다. 이는 아직 공개 원본이 아니지만 저장 공간을 사용하기 때문입니다. 잔재는 자동 삭제하지 않습니다. 원본 무결성 도구는 이런 잔재를 UNEXPECTED_ENTRY로 보고하며 정상 원본으로 인정하지 않습니다. 서버/외부 writer를 중지하고 운영 점검 후 별도의 승인된 절차로 처리합니다. 이번 개발에서는 실제 저장소의 잔재를 삭제하지 않습니다.

카탈로그 오류·본문 크기 불일치·알 수 없는 파일/하위 구조·심볼릭 링크/정션·열거 상한 초과를 사용량0으로 처리하지 않습니다. 해당 조직 등록을503으로 거절합니다. 조직 하나의 스캔은 디렉터리와 파일을 합쳐100000개 항목으로 제한하며 파일 해시나 전체 디코딩은 하지 않습니다. 기존 SHA-256 대조는 ORIGINAL_INTEGRITY.md의 오프라인 도구로 수행합니다. 대량 자료의 등록 비용은 운영 샘플로 별도 측정하고, 상한을 넘는 저장소에는 트랜잭션 가능한 별도 카탈로그/계수 저장소가 필요합니다.

## writer 경계와 조회 속도

활성화한 LocalMediaStore는 originals/.quota-writer.lock의 OS 파일 잠금을 전체 수명 동안 유지합니다. 같은 경로를 사용하는 다른 quota 활성 writer는 기동을 거절합니다. 정상 종료 시 해제하고 잠금 파일은 빈 상태로 유지합니다. 무결성 점검 도구는 canonical regular file인 빈 잠금만 저장소 기반 파일로 인식합니다. 잠금 파일을 삭제해서 실행 중인 잠금을 우회하지 않습니다.

단일 로컬 writer 배포가 전제입니다. 모든 writer에 같은 활성 설정을 적용하고, quota 비활성 앱/관리자/외부 프로그램이 같은 원본 경로를 수정하지 않도록 서비스 계정·ACL을 관리합니다. 파일 잠금은 임의 OS 프로그램을 격리하는 수단이 아닙니다. 여러 노드/네트워크 파일시스템·공유 쓰기는 지원하지 않으며 DB/객체 저장소의 원자적 계수 계약으로 별도 설계해야 합니다.

사용량 확인과 예약 monitor는 업로드에만 적용합니다. 원본/PNG/썸네일 GET/HEAD·영상/음성 Range·권한 확인 경로에는 추가 계수 스캔이나 잠금을 넣지 않습니다. 디스크/CPU 자원 공유로 인한 운영 부하까지 없어진다는 의미는 아니므로 실제 동시 등록·뷰잉 P95는 별도 인수 대상입니다.

## 검증 범위

합성 임시 저장소에서 조직/소유자 합산·정확한 경계·다른 조직·동시 예약/실패 해제·중복 해제·원자 게시·재시작/한도 축소·중단 잔재 합산·손상/미확인 파일·Windows 정션·writer 중복 거절/정상 재획득을 검증합니다. API에서는507/no-store/진단 비노출·다른 조직 후속 등록·인증/CSRF 유지를 검사합니다. 정리 불확실성의 후속 차단은 계수 정책 테스트로 확인하며 실제 운영 디스크 장애를 발생시키지는 않습니다. 설치 옵션의 기본/음수/최대 초과도 검사합니다. 운영 SSO·여러 JVM/실제 강제 종료·업무 대용량/P95·OS 물리 할당량은 별도 검증입니다.

최종 검증(2026-10-22): JDK21 build -Pimg2tileIntegration -PffmpegIntegration 성공. Java330개(이번 단계 신규16개), 실패/오류/건너뜀0. 실제 img2tile·FFmpeg와 라이선스16개 규칙·63개 구성요소/53개 포함 JAR 기준선 검사 통과. 뷰어 안내 문구 JS 구문 검사/JAR 반영과 테스트 fixture 실행 JAR 미포함 확인. 브라우저 시나리오·운영 부하·실제 강제 종료/다중 JVM 인수는 재실행하지 않았고 실제 원본/잔재 삭제 및 설치 ZIP 생성은 수행하지 않았습니다.

중단 staging의 운영 목록은 [UPLOAD_RESIDUE_INSPECTION.md](UPLOAD_RESIDUE_INSPECTION.md)의 읽기 전용 명령으로 확인할 수 있습니다. 이 명령은 원본/카운터를 변경하거나 할당량을 반환하지 않으며 결과를 자동 삭제 판정으로 사용하지 않습니다.
