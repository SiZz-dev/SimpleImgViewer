# 무결성 검사 구간 계측과 제한 병렬 읽기

후속: [동시 열람 이벤트 루프·API 응답성 검증](RUNTIME_RESPONSIVENESS.md)을 완료했다. 아래의 다음 단계 설명은 본 비교 시점 기록이며, 최신 결과와 Worker Thread 후보 비교 계획은 후속 문서를 따른다.

2026-11-16. 관리형 런타임의 전체 파일·바이트 검증을 유지하면서 비용을 구분하고 파일 단위 병렬 읽기를 비교했다. 기본값은 파일2개, 각1MiB 버퍼다. `readChunkBytes`, `fileConcurrency`, `observe`는 내부 util 옵션이며 YAML/HTTP에서 받지 않는다. 새 의존성·다운로드·설치 ZIP은 추가하지 않았다.

## 구현 경계

`conversion/util.runtime-inventory.verifyRuntimeTree`가 먼저 전체 디렉터리 목록과 경로·유형·크기·링크를 검사한 후, 제한된 worker가 파일을 순차 배정받는다. 각 파일은 열기 직전에 lstat/realpath와 핸들 stat을 다시 확인하고, 같은 핸들로 끝까지 읽어 총 바이트 수와 SHA-256을 대조한다. 기본 병렬 작업은 최대2개로 검증 호출당 읽기 버퍼 합계 최대2MiB이며, 비교 시험의 내부 한도는4개다. 파일 수나 입력 요청 수에 비례해 worker를 추가하지 않는다. 서로 다른 버전의 검증이 겹치면 각 호출에 별도 상한이 적용된다.

한 worker가 실패하면 새 파일 배정을 멈추고, 이미 열린 다른 worker의 읽기·핸들 닫기가 모두 끝난 후 오류를 반환한다. `Promise.allSettled`로 이를 보장해 RuntimeVersions 사용 참조가 남은 읽기보다 먼저 해제되지 않도록 한다. 이전의 완료 검증 캐시 부재, 진행 중인 동일 버전 검증 공유, 게시 전 재검증과 부분 회수 정책을 유지한다.

`observe`는 고정 구간의 시간·파일 수·바이트 수·읽기 횟수·성공 여부만 한 번 전달한다. 호스트 파일 경로나 원본·사용자 식별자를 전달하지 않고, callback 오류도 검증 결과를 바꾸지 않는다. 기본 경로에서는 관측 callback과 구간 시계 호출이 없다. `ManagedRuntimes.verifyNoteFont`는 기존 승인 폰트 검사를 그대로 호출하는 내부 경계로, 시험에서만 호출 시간을 관측한다.

## 재현과 측정 조건

기존 승인 합성 런타임 카탈로그와 현재 LPAC 이미지/미디어 빌드 manifest가 필요하다. 실제 설치 YAML과 IntelliJ 실행 서버는 변경하지 않는다.

```powershell
$env:SIV_SPEED_YAML = '.tools/load/<fixture ID>/<run ID>/lpac.yml'
& '.tools/runtimes/node-24.22.1/node.exe' scripts/test-runtime-verification-profile.mjs
```

새 저장소·LPAC 풀의 localhost 임시 포트 서버에서 PNG 업로드·실제 변환 후 캐시 manifest를 비교한다. 1/2/4개 후보별 계측 활성6회, 비활성6회씩 후보 순서를 회전·반전했다. 별도 Node/브라우저 회귀는 측정 종료 후 실행했다. 활성 계측에서 descriptor의 전체 파일 수·바이트 수와 결과가 일치하는지 관측 callback 밖에서 검사한다. 캐시 manifest마다 전체 트리 검증1회, 동일 메타데이터, decoder 재실행0회, 비공개 PNG 읽기를 확인한다.

개발 PC는 Windows x64 `10.0.26300`, Intel Core i5-8250U다. 원시 표본은 `build/reports/runtime-verification-profile/verification.json`에 기록한다. 다음 값은 loopback의 소규모 시험 중앙값이며 SLA나 운영 부하 처리량 보장값이 아니다. 앞선 읽기 크기 시험과는 실행 조건·파일 열기 전 재검사 구현이 달라 이번 시험 안의 후보끼리 비교한다.

## 결과와 기본값

| 계측 비활성, 후보별6회 중앙값 | 파일1개 | 파일2개 | 파일4개 |
| --- | ---: | ---: | ---: |
| 페이지 manifest HTTP·본문 읽기 | 643ms | 595ms | 547ms |
| 전체 트리 검증 | 563ms | 513ms | 467ms |
| 승인 폰트 검사 | 56ms | 59ms | 58ms |

별도 시험에서 Node·FFmpeg 버전을 동시에 acquire하고 모두 release했다. 후보별4배치 중앙값은 파일1개1155ms, 파일2개1008ms, 파일4개996ms다. 이 값은 런타임 검증 배치이며 이미지·영상 변환 전체 시간이나 동시 사용자 처리량이 아니다. 같은 버전을 중복 요청하는 조건과도 구분한다.

파일2개는 manifest 약7.5%, 서로 다른 두 런타임의 동시 검증 약12.7% 개선을 보였다. 파일4개는 단일 요청에서 더 빨랐지만 동시 검증은2개보다 약1.2% 추가 개선에 그쳤다. 기본값은 읽기 버퍼 상한을2MiB로 제한하는2개로 선택했다. 프로파일 옵션은 설치 튜닝 기능으로 공개하지 않았다.

## 구간별 비용 해석

| 계측 활성·파일1개,6회 중앙값 | 시간 |
| --- | ---: |
| root 경로 검사 | 4ms |
| 전체 목록·경로·속성 검사 | 66ms |
| 파일 열기 전 재검사·open/stat | 91ms |
| 파일 핸들 read 대기 | 72ms |
| SHA update/digest | 342ms |
| 전체 트리 검증 | 588ms |
| 별도 승인 폰트 검사 | 70ms |

각 구간 중앙값을 더해 전체 중앙값과 일치한다고 해석하지 않는다. 파일 닫기·배정·구간 밖 처리도 전체 시간에 포함된다. 병렬 후보의 구간 시간은 worker별 누적 대기 합계이므로 전체 벽시계보다 클 수 있다. 계측 활성/비활성은 별도 표본이어서 그 차이를 정확한 계측 오버헤드로 간주하지 않는다. SHA 연산이 주된 비용이며, 현재 SHA update는 Node 메인 스레드에서 동기 실행한다.

## 검증과 후속 작업

전체 Node/네이티브120개(실패/건너뜀0), 실제 Chrome13개 시나리오, React production 빌드와 npm90개 라이선스 기준선을 통과했다. 새 테스트는 후보별 전체 바이트 검증, 관찰자 오류 격리, 잘못된 병렬 한도 거절, 한 파일 변조 실패 중 다른 열린 읽기 종료 대기를 확인한다. 기존 같은 크기 경계·꼬리 변조와 링크/미등록/누락/부분 회수, 참조/회수 경쟁 테스트도 유지했다. 최종 기본값의 LPAC 서버 기동·실제 신규 이미지 변환·비공개 PNG도 별도로 통과했고 결과는 같은 보고서 디렉터리의 default-smoke.json에 기록했다.

다음 단계는 동시 열람 상황에서 메인 스레드 SHA 연산의 이벤트 루프 지연과 일반 API 응답성을 측정하고, 결과에 따라 해시 계산 분리 후보를 검토하는 것이다. 운영 Windows·서비스 계정별 인수는 계속 남아 있다.
