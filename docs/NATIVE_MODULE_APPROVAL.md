# 외부 모듈 기준선·변경 감지·재승인

2026-10-23 추가. img2tile과 FFmpeg/FFprobe가 서버 시작 시 모듈 내용 기준선을 고정하고, 실행 중 설치 파일 변경을 기존 승인/캐시 식별로 자동 수용하지 않도록 합니다. 설치 파일을 쓰거나 자동 교체·다운로드·업데이트·설정 수정하는 기능은 추가하지 않습니다.

## 기준선 범위

NativeModuleSnapshot은 아래 파일의 경로/정체성/크기/수정 시각과 SHA-256을 고정합니다.

| 대상 | 포함 |
| --- | --- |
| 실행 파일 | 실제 선택된 EXE. img2tile 1개, FFmpeg/FFprobe 2개 |
| 인접 라이브러리 | 각 실행 파일 부모 폴더의 직접 .dll, .so, .so.*, .dylib 파일 |
| img2tile 리소스 | resource 디렉터리의 직접 일반 파일 전부. cmyk.icc/libc9i.xml을 포함 |
| 제외 | 사용하지 않는 인접 EXE(ffplay 등), 로그·작업 폴더, System32 등 외부 시스템 라이브러리, 인접 DLL 하위 폴더의 의존성 |

일반 파일/정규화된 절대 canonical 경로/NOFOLLOW를 적용합니다. module/resource 폴더의 정체성(fileKey/생성 시각)도 확인합니다. resource의 하위 디렉터리·링크/정션/특수 파일은 지원하지 않고 실패합니다. img2tile은 시작 시 필수 cmyk.icc/libc9i.xml이 일반 파일/각4 MiB 이하인지도 확인하며 불완전한 설치는 데이터 저장 경로를 생성하기 전에 시작을 거절합니다. 파일 목록/범위가 바뀌면 자동 제외하거나 다른 모듈로 우회하지 않습니다.

고정 상한: 실행 파일1~8개, 선택 파일 총256개, 파일당256 MiB, 전체512 MiB, 루트/리소스 열거 합계4096개 항목. 해시는32 KiB 버퍼로 크기만큼 읽고 성장/잘림과 전후 속성을 재확인합니다. 상한 초과·불완전 판독·권한/경계 실패는 UNAVAILABLE로 처리합니다. 실제 현재 D:/DG_module의 img2tile·FFmpeg 배치로 통합 검증하며 EXE/DLL은 저장소에 포함하지 않습니다.

## 신뢰와 승인 의미

FFmpeg EXE 두 개는 기존 YAML ffmpeg-sha256/ffprobe-sha256과 상한 있는 시작 snapshot에서 계산한 전체 해시를 대조한 뒤에만 native 빌드 검사를 실행합니다. LGPL shared/필수 인코더·도구 버전 승인 검사는 그대로 유지합니다. 별도 EXE 해시 루프를 반복하지 않고 같은 snapshot 바이트를 설정 핀과 캐시 내용 식별의 근거로 사용합니다.

인접 DLL과 리소스는 **신뢰된 설치 경로의 시작 시 로컬 기준선**입니다. 이 기능은 공급자 서명이나 보호된 외부 bundle manifest를 검증하는 도구가 아닙니다. 재시작만으로 DLL의 출처/라이선스를 인증하지 않으며, 설치 담당자가 사전 검토한 모듈만 읽기 전용 경로에 배치해야 합니다. img2tile은 사용자가 내부 개발 모듈 사용을 확인한 기존 정책을 유지합니다. ImageMagick 실행/자동 대체는 추가하지 않습니다.

## 실행과 실패 정책

| 시점 | 검사 |
| --- | --- |
| 시작 | 파일 집합/전체 SHA-256을 고정하고 전후 안정성 확인. FFmpeg는 빌드 승인 후에도 전체 내용 재확인 |
| 새 변환 시작 | 전체 파일 목록/속성/내용 해시를 시작 기준선과 비교. 불일치 시 native 실행 전 실패 |
| 각 native 호출 전후 | 고정 파일 목록/정체성/크기/수정 시각 비교 |
| img2tile resource 복사 | 작업 폴더에 복사한 바이트가 시작 기준선의 리소스 SHA-256/크기와 일치하는지 확인 |
| 성공 결과 반환 전 | 전체 모듈 목록/내용을 다시 확인. 정상 출력이 있어도 모듈이 바뀌면 결과를 반환하지 않음 |

파일 추가/삭제/교체·속성 또는 내용 변경·검증 I/O 실패를 한 번 발견하면 해당 snapshot을 사용 불가로 고정합니다. 원래 바이트를 복원해도 같은 converter/engine은 자동 재승인하지 않습니다. 후속 검사/새 변환은 UNAVAILABLE로 실패하고, 운영자가 검토한 설치로 재시작해 새 인스턴스를 구성해야 합니다. 단순 작업 재시도는 모듈을 재기준화하지 않습니다.

사용자 작업 취소로 인한 InterruptedIOException은 인터럽트 상태를 보존하며 정상 모듈 전체의 승인을 취소하지 않습니다. 공유 snapshot은 불변 기준선/원자적 사용 불가 표식을 사용하므로 여러 워커가 기준선을 갱신하지 않습니다. 경로·원시 OS 메시지·SHA·프로세스 출력은 모듈 변경 오류에 포함하지 않습니다.

실행 실패한 작업 폴더에 파일이 남아 있어도 검증된 결과로 게시하지 않습니다. 기존 서비스가 실패 상태·감사/정리 수명을 처리합니다. 실제 운영 모듈에 테스트 변경을 가하지 않습니다.

## 캐시와 뷰잉 속도

내용 식별자는 native-module-v1/과 선택 파일의 상대 이름/크기/SHA-256에서 만든 해시입니다. 절대 설치 경로·파일 시각을 식별자에 넣지 않습니다. 동일 내용 재설치는 동일 식별자를 만들고, EXE/DLL/리소스 내용/목록이 바뀌면 새 식별자가 됩니다.

- img2tile cacheIdentity는 시작 snapshot의 고정 식별자를 사용하며 확인 호출 때 내용 일치도 검사합니다. PreviewQueue의 시작 engine 식별자에 포함됩니다.
- FFmpeg identity는 기존 설정/빌드 버전에 모듈 내용 식별자를 더합니다. 서버 인스턴스 안에서 파일 교체를 따라 동적으로 바꾸지 않습니다.
- 새 작업은 모듈 검증을 통과해야 하며, 변경된 모듈로 생성한 결과를 과거 키로 반환/게시하지 않습니다.
- 이미 완료한 검증 캐시의 GET/HEAD/Range·상태 조회에는 모듈 전체 해시를 추가하지 않습니다. 같은 인스턴스의 기존 완료 캐시는 기존 파일 권한/무결성 정책으로 계속 조회할 수 있습니다. 이 기능은 완료 캐시 자동 삭제/권한 철회를 수행하지 않습니다.
- 검토 후 다른 내용의 모듈로 재시작하면 새 키로 준비하며 기존 캐시는 알려진 캐시 유지보수/보관 정책의 대상입니다. 최초 이 정책 도입도 기존과 키 구성이 달라 한 번의 재준비가 필요할 수 있습니다.

전체 해시는 새 native 작업의 시작/끝과 초기 승인에서 수행하므로 기존 캐시 뷰잉에는 I/O를 더하지 않지만 새 변환에는 비용이 추가됩니다. 각 호출 전후는 가벼운 목록/속성 검사입니다. 최대 파일 집합을 기준으로 작업당 본문 해시 재읽기는 대략2×512 MiB이고 초기 기준선/FFmpeg 빌드 검사 후 재확인·리소스 복사 대조는 별도입니다. 모듈 파일 I/O는 native 프로세스 timeout으로 강제 제한되지 않으므로 안정적인 전용 로컬 설치 경로를 사용하고 점검 시간을 운영 부하 인수에 포함합니다. 업무 P95를 이번 합성 결과로 대체하지 않습니다.

## 모듈 교체 절차

1. 신규 요청/변환 접수를 중지하고 모든 서버/워커·변환 프로세스를 정상 종료합니다. 실행 중 EXE/DLL을 덮어쓰거나 감시 서비스가 부분 배포하지 않게 합니다.
2. 공급원·라이선스·서명/보호된 외부 파일 목록·EXE/DLL/리소스의 해시와 호환성을 별도 검토합니다. 변경 전 배포본/설정과 업무 데이터의 백업 기록을 보존합니다.
3. 검토한 전체 모듈 세트를 전용 경로에 배치합니다. 서비스 계정에는 모듈 읽기/실행만 허용하고 작업/출력 경로만 쓰도록 OS ACL을 적용합니다. 네트워크·CPU/메모리 하드 격리는 별도 운영 인수입니다.
4. FFmpeg EXE가 바뀌었다면 신뢰된 기대 해시에 맞춰 실제 설치 YAML 두 SHA를 운영자가 갱신합니다. 실제 config/imagegate.yml을 저장소에 넣거나 도구가 기록 해시를 자동 수정하지 않습니다. DLL만 바뀌어도 전체 검토가 필요합니다.
5. 재시작 시 모든 시작 검사가 통과해야 합니다. 기존 실패 인스턴스를 되살리거나 자동 우회하지 않습니다. 다른 버전의 FFmpeg/FFprobe나 승인되지 않은 빌드는 계속 거절합니다.
6. 격리/승인된 환경에서 합성 TIFF·MP4/MPEG·MP3/WAV의 변환/재생·seek와 권한·감사/용량을 검증하고, 새 키로 필요한 자료를 명시적으로 준비합니다. 검증 후 업무 트래픽을 전환합니다.

실제 설치 설정/모듈 교체·권한 변경·업무 파일 재생성은 이 개발 단계에서 수행하지 않습니다.

## 한계와 검증

검사 사이의 파일 교체, 속성/내용을 의도적으로 되돌리는 경쟁, OS DLL 로딩 경로 전체, native 코드의 다른 파일/네트워크 접근을 원자적으로 격리하지 않습니다. 시작 기준선을 만드는 순간의 설치 자체가 신뢰돼야 합니다. [외부 실행 경계](EXTERNAL_PROCESS_SECURITY.md)의 OS 계정/ACL/하드 제한이 계속 필요합니다.

테스트는 합성 모듈의 동일 크기/mtime 복원 변조·DLL 추가/삭제·resource/복사본 변조·변경 후 원상복구 시에도 기존 인스턴스 거절·새 인스턴스 식별 분리·정션/목록 상한·취소 시 정상 승인 유지, adapter/engine 실행 전·중간·게시 전 차단 및 실제 모듈 호환성을 확인합니다. 실제 D:/DG_module 파일은 읽기만 합니다.

2026-10-23 검증: JDK21 build -Pimg2tileIntegration -PffmpegIntegration 성공. 신규20개(snapshot9/img2tile4/FFmpeg6/설치1), 전체 Java457개 통과(실패/오류/건너뜀0). 실제 img2tile·FFmpeg/FFprobe와 라이선스16개 규칙/63개 구성요소·53개 포함 JAR 기준선 검사 통과. 최종 실행 JAR에서 모듈 snapshot을 로드해 동일 크기/mtime 내용 변경·복원 후에도 기존 인스턴스 거절·새 인스턴스 내용 식별 분리·DLL 목록 변경 거절을 확인했고 테스트/fixture runtime JAR 항목0개. 실제 D:/DG_module·실제 설치 YAML·업무 파일은 변경하지 않았으며 UI/운영 P95 재측정·설치 ZIP 생성은 수행하지 않음. 로컬 기준선은 공급자 서명/외부 bundle 승인을 대체하지 않으며 distributionReady=false 유지.
