# 동일 JVM·원본의 PNG 복사 교차 검증

2026-10-28. 이전 별도 실행의16.97→18.52초 관측만으로 변경 효과/환경 변동을 구분할 수 없어, 실제 native 타일 준비를 한 JVM에서 교차 실행했습니다. 운영 PNG 처리·압축/검증/저장 정책은 변경하지 않았습니다.

## 재현과 비교 조건

```powershell
$env:JAVA_HOME = 'C:/Program Files/Java/openjdk/jdk-21.0.2'
.\gradlew.bat pngCrossoverTest
```

Windows/실제 승인 img2tile 설치가 필요한 선택 작업으로 일반 build/test에는 포함하지 않습니다. pngCrossoverPairs는2/4/6(기본4)이며, 기준 먼저/전용 버퍼 먼저를 같은 횟수로 배치합니다. 테스트 JVM은 최소256MiB/최대1GiB입니다. 일반 운영 설정/인증이나 변환 모듈을 바꾸지 않습니다.

- 24MP 합성 TIFF 한 파일·같은 등록 ID/버전/actor·같은 변환기와 공유 실행기1개를 사용합니다.
- 기준 복사1회·전용 버퍼1회 워밍업 후4쌍/8회를 측정합니다. 순서는 기준→전용, 전용→기준을 번갈아 적용합니다. 명시적 System.gc는 호출하지 않습니다.
- 매 실행의 캐시/작업 저장소를 새로 만들어 준비 완료 캐시에 의해 정규화가 생략되지 않게 합니다. 디렉터리 생성/생성자·등록/워밍업은 측정 밖입니다.
- render 전체(native 실행·입출력 검증·정규화·force·원자 게시·작업 정리)의 경과/렌더 스레드 CPU·할당 바이트와 JVM GC 횟수/시간 차이를 기록합니다. 상세 진단 관측자는 두 모드 모두 null입니다.
- 게시 후 manifest의 각 PNG SHA를 순서대로 집계한 해시가 모든 실행에서 같은지 확인합니다. 모든 측정이 끝난 뒤10개 결과(워밍업 포함)의 실제 PNG 바이트/SHA와 전체 픽셀·원본 SHA를 독립적으로 검증하여 후처리 디코딩 할당을 다음 측정에 섞지 않습니다.

할당량은 실제 com.sun.management.ThreadMXBean의 지원 여부/음수 여부를 검사한 뒤 수집합니다. 렌더 스레드의 Java 누적 할당이며 다른 스레드/native 할당·RSS/살아 있는 힙 최고치가 아닙니다. GC 수치는 JVM 전체이므로 특정 모드에 독점적으로 귀속하지 않습니다. OS 페이지 캐시·디스크/데스크톱 부하·시간대 변동은 여전히 통제하지 못하며, HTTP/브라우저/SSO 시간을 포함하지 않습니다.

## 코드·보안 경계

TilePyramidPublisher의 package-private Normalizer/생성자는 이 통제 비교에서만 기준 복사를 연결하는 경계입니다. 공개 생성자는 항상 TilePngSanitizer를 사용하며 YAML/HTTP로 기준 모드를 선택할 수 없습니다. 기준 구현은 src/test의 ReferenceTilePngNormalizer와 기존 테스트 후보에만 존재합니다. 기존 공개 API/모듈 선택·캐시 포맷·native 승인 기준은 바뀌지 않습니다.

대체 정규화기를 사용해도 최초 native 검증·정규화 직전 원본 SHA/경계 확인·공개 cache PNG/메타데이터·크기 검사·게시 직전 원본/모듈/권한·commit gate 검사는 유지합니다. 정상 PNG에 private text를 그대로 남기는 후보, 손상/과대/null 출력이 게시되지 않는지와 native 입력 검증이 정규화보다 먼저 수행되는지를 정규 회귀로 확인합니다.

원시 결과는 build/reports/png-crossover/latest.json, 쌍별 집계는 summary.json입니다. 합성 자료는 build/png-crossover-work/run-* 아래에 생성되어 Gradle clean 대상입니다. 원본 식별자/비밀정보/파일 경로를 JSON 보고서에 기록하지 않습니다. 설치 ZIP은 최종 단계에만 생성합니다.
